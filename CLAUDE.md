## Commands

```bash
npx expo start            # dev server (see "Do NOT use Expo Go" below)
npx expo run:ios           # build + run dev client on simulator/device
npx expo run:android       # build + run dev client on Android
eas build --platform ios --profile preview      # .ipa for internal distribution
eas build --platform android --profile preview  # .apk for internal distribution
eas update --branch production --environment production --message "..."  # push JS/UI-only update (no native changes; SDK 55+ requires --environment)
```

There is no test suite, linter, or typechecker configured in this repo — `package.json` only has the four scripts above (`start`, `android`, `ios`, `web`).

**Do NOT use Expo Go.** This app depends on native modules (`expo-audio`, `expo-location` background geofencing) that Expo Go cannot run. Use a dev client build (`expo run:ios` / `expo run:android`) or an EAS build instead.

This project targets **Expo SDK 56**, which changed significantly from earlier SDKs (e.g. `expo-audio` replaces `expo-av`, `expo-file-system/legacy` is required for the old `FileSystem.writeAsStringAsync`/`uploadAsync` API). Always check current usage against https://docs.expo.dev/versions/v56.0.0/ before assuming an API from a prior SDK still applies.

## Architecture

**This is a thin native client over an existing web app's backend**, not a standalone app with its own API. There is no backend code in this repo — all server logic lives in Netlify functions hosted at `app.clickpickandcook.com/.netlify/functions/`. See [DATAMODEL.md](DATAMODEL.md#api-reference) for the full endpoint-by-endpoint reference (request/response shapes, every call site). One exception worth knowing up front: Groq Whisper transcription (`useContinuousMic.js`) is called **directly from the client** (`api.groq.com`, with `EXPO_PUBLIC_GROQ_KEY` embedded as a bearer token) rather than proxied through a Netlify function — everything else goes through `clickpickandcook.com`.

Supabase is used in two different, inconsistent ways:
- `src/hooks/useAuth.js` calls the custom `auth` Netlify function for login (not Supabase), but uses `supabase.auth.signUp`/`signOut` directly for signup/logout. It instantiates its own `createClient` separately from `src/lib/supabase.js` (which uses `expo-secure-store` for token storage, vs. `useAuth`'s own client using `AsyncStorage`). Be aware these are two distinct Supabase client instances with different storage adapters — don't assume changes to one affect the other.

**Local-first data with legacy storage keys.** `src/hooks/useSync.js` is the source of truth for app data: it loads a cached snapshot from `AsyncStorage` (`fern_sync_cache`) instantly, then silently refreshes from the `sync` Netlify function in the background. Pushes go through `pushChangedFromStorage`, which reads individual `AsyncStorage` keys, merges in changed fields, and POSTs the whole payload back. The individual key names (`rv4_saved`, `rv4_books`, `rv4_meal_plan`, `rv4_master_shop`, `remi_explicit`, `cpc_followed_bloggers`, `cpc_user_stores`) are carried over from the web app's own storage scheme (`rv4` = recipe vault, `remi` = an earlier assistant name, `cpc` = clickpickandcook) — they're required for sync compatibility with the web app, not arbitrary. `useAuth.js` independently writes the same keys after login/signup via its own `syncPull`, and it has genuinely drifted from `useSync.pull()` — it never writes `fern_sync_cache`, skips the corrupted-emoji repair pass, and signup can clobber a fresh `remi_explicit.userName` write with an empty server profile. See [DATAMODEL.md](DATAMODEL.md#usesyncjs-vs-useauthjs-known-divergence) for the exact divergence; keep the two write paths in sync if you touch either.

**Voice pipeline.** There are two parallel hooks for the same Groq-backed voice loop:
- `useContinuousMic` — always-listening hands-free mode with voice-activity detection (silence threshold `SILENCE_DB`/`SILENCE_MS` in the hook, auto-stops after `MAX_RECORDING_MS`), records via `expo-audio`, uploads to Groq Whisper directly from the client (`EXPO_PUBLIC_GROQ_KEY`), then round-trips through `ai` and `fern-speak` for a spoken reply, and re-arms itself after playback finishes. Gated at the `fern_voice_enabled` AsyncStorage flag (set from `AccountScreen`).
- Ask Fern chat replies are spoken via `src/utils/spokenSummary.js` (first sentence or two, max ~220 chars; the full reply is still shown on screen) because Azure speech is billed per character.
- **Free Ask Fern limit:** Free users get 5 Ask Fern questions per local day (`ChatSheetModal.askFern`, device-only counter `fern_free_chat_count`; the silent auto-opener never counts; Pro and up unlimited). The 6th shows an `UpgradeGateModal` with `chat_limit_*` copy.
- **Free recipe / cookbook limits:** Free can hold 20 saved recipes and 1 cookbook (`src/utils/freeLimits.js`, counted from `rv4_saved` / `rv4_books` on the device; existing users keep what they have, only adding more is blocked). Gates: `RecipeDetailModal` (save of a not-yet-saved recipe, `recipe_limit_*`), `ImportScreen` (before the cookbook picker), `HomeScreen.handleHomeAddFoundRecipe` (silently skips the library save when full, still adds the meal), `RecipesScreen` New Cookbook button (`cookbook_limit_*`). Pro and up unlimited.
- **Spoken replies are Pro and up** (they cost per character): `useFernVoice` and `useContinuousMic` check `hasAccess(TIERS.PRO)`, so Free users get text only (no `fern-speak` calls, and `useContinuousMic` skips its own AI+speak round trip; mic transcription itself is still available). `TourModal` passes `allowFree: true` so the intro tour is still read aloud to everyone.
- `useFernVoice` — a simpler one-shot "speak this text" / "get a reply, optionally speak it" hook used by individual screens (no recording/VAD).

Both write synthesized speech to a local mp3 in `FileSystem.cacheDirectory` (manual base64 decode, since `expo-file-system/legacy` is used) and play it with `expo-audio`'s `useAudioPlayer`.

**Store-arrival detection (geofencing).** Two layers share one 30-minute per-store cooldown (`claimArrival`, AsyncStorage `fern_geofence_last_notified`):
- `src/services/storeGeofencing.js` registers the user's saved stores (`cpc_user_stores`, nearest 20, 300 m radius (`GEOFENCE_RADIUS_M`; raised from 150 m on 2026-10-14 because iOS reports entry late)) as **OS-level geofences** via `Location.startGeofencingAsync`, so iOS/Android wake the app in the background (even when closed) and a local "you've arrived" notification is posted. Needs the "Always" location permission. **Android builds ship without background location** (`ACCESS_BACKGROUND_LOCATION` blocked in `app.json`, `isAndroidBackgroundLocationEnabled: false`, to avoid Google Play's background-location declaration and video); there the setup screen skips the "Always" step (`needsAlways` in `locationSetup.js`) and store alerts come only from the foreground poll while the app is open. Turn it back on (permission, plugin flag, declaration + demo video) to restore Android background alerts. The task (`fern-store-geofence`) is defined with `TaskManager.defineTask` in the **global scope** of that module, which `index.js` imports before `registerRootComponent` — it must not be moved into a component or a lazy import, because when the OS relaunches the app headless no React tree is mounted (and expo-task-manager unregisters tasks it finds undefined). `expo-task-manager` is loaded with a guarded `require` so a native build that predates it falls back to the foreground poll instead of crashing.
- **Permissions are asked on `LocationSetupModal`** (`src/services/locationSetup.js`: location → "Always" → notifications, with an explanation), shown from `App.js` after login when anything is missing, at most once a day (`fern_location_setup_last`, device-only). `useGeofence.start()` no longer prompts by default — it only uses what was already granted (`start({ prompt: true })` still asks). JS-only; OTA is enough. **"Always" nudges (iOS):** the screen explains the benefit (store alerts with the app closed); when "While Using" is already granted but Always isn't, it skips straight to the "Open Settings" button (iOS asks for Always only once); and `src/components/home/AlwaysLocationReminder.js` (passed to `NewHome` as `notice`) shows a Home card to **Pro Max** users on iOS while Location isn't Always — "Open Settings" / "Not now" (hidden for the day via device-only `fern_always_reminder_last`), re-checked when the app returns from Settings.
- `src/hooks/useGeofence.js` (used by `App.js`) requests permissions, registers the OS geofences, re-registers when the stores list changes, and keeps a 2-minute foreground GPS poll as a fallback (users with only "While Using" permission, and "already inside the store when the app opened", which a geofence can't report). `App.js` handles a tap on the arrival notification (`data.type === 'store_arrival'`): **Update 2026-10-14:** a tap on the arrival notification now navigates to `Home` with `scanFlyerStore`/`scanFlyerAt` (not `Shopping`), and `HomeScreen` calls `chooseFlyerStore(store)` for that saved store — the same flyer scan as tapping the store row on Home (this week's flyer if already scanned, else the photo prompt); the exit/everyday taps still go to `Shopping`. (The older description follows, now historical:) **Pro Max** (bought or admin-granted — `hasAccess(FEATURE_TIERS.personal_shopper)`) navigates to `Home` with `openPersonalShopperArrival: { store }`, which `HomeScreen.js` turns into opening `PersonalShopperModal` with `startWithCircular` — the modal skips its intro, asks for a flyer photo (camera/library/skip), scans it with `scanCircular`, first checks `store-deals` for this week's ad already scanned (by anyone) for the user's saved stores and offers to use it instead of asking for a photo, then asks a few tap-to-answer "About you" questions (people, diet/avoid, how many dinners, kind of week — remembered in `fern_shopper_prefs` and confirmed next time), then runs the usual flow (staples → dinners → week → ingredients → list) with the sale items passed to `suggest_dinners` as `deals`. **Free/Pro get no store notification at all** (arrival and "you saved $X" alerts are Pro Max only, gated in `storeGeofencing.notifyArrival`/`notifyDeparture`); the tap-handler upsell branch (`fern_arrival_upsell_last`) is now only reachable from an older notification. The tap handler waits for RevenueCat to finish loading (and ~1.2 s on a cold start) before choosing. The notification body itself is also tier-aware (`geofence_arrived_body_pro_max`, read from the device-only tier keys in `storeGeofencing.js`). `App.js` also calls `stopStoreGeofencing()` on sign-out. Changes here need a **native build** if the installed build predates `expo-task-manager`/`UIBackgroundModes: location`; a JS-only OTA is enough otherwise.

## Features (modals)

Nearly every premium feature is a controlled modal component in `src/components/modals/`, rendered from `HomeScreen.js` (unless noted) and receiving all state/handlers as props rather than owning its own fetch logic. Every gated modal follows `if (visible && !hasAccess(TIER)) return <UpgradeGateModal .../>` and calls `maybeAutoStart('<tour_key>')` from `TourContext` on open (tour keys/content live in `src/constants/tourContent.js`). Tiers are `FREE` / `PRO` / `PRO_MAX` (`src/constants/tiers.js`); `useEntitlement()` is the single choke point every gate reads through, backed by RevenueCat (`src/services/RevenueCatContext.js` + `src/services/purchasesService.js`). There is one RevenueCat entitlement, `"Fern Pro"` (`src/constants/revenuecat.js`'s `ENTITLEMENT_ID`) — PRO vs PRO_MAX is derived client-side from *which product* granted it (`PRODUCT_TIER`: `fern_pro_monthly` → PRO, `fern_pro_max_monthly` → PRO_MAX), not from a second RevenueCat entitlement. Both plans are monthly-recurring — Pro Max isn't a longer commitment, it's more features at a higher monthly price ($2.99 vs $6.99, per `plans_pro_price`/`plans_pro_max_price` in translations.js) — there is no yearly/lifetime plan. Because RevenueCat's built-in package types (`$rc_monthly` etc.) only fit one product per type per Offering, the dashboard's default Offering must use two CUSTOM packages instead, identifiers `pro_monthly`/`pro_max_monthly` (`PACKAGE_IDS` in `revenuecat.js`). Store-facing display name/description copy for both products (EN+ES) lives in `PRODUCT_DISPLAY` in the same file. `RevenueCatProvider` is mounted in `App.js` above the auth gate (configures the SDK anonymously on mount, then `Purchases.logIn`s the real user id once auth resolves, `logOut`s on sign-out). `UpgradeGateModal` presents the native RevenueCat Paywall (`presentPaywall()`) as its primary CTA; `PlansScreen`/`AccountScreen` add a "Manage Subscription" entry (RevenueCat's Customer Center) and a "Restore Purchases" action. The RevenueCat public SDK key lives in `EXPO_PUBLIC_REVENUECAT_IOS_KEY`/`EXPO_PUBLIC_REVENUECAT_ANDROID_KEY` (`.env`, gitignored — same pattern as the Supabase/Groq keys). Since `react-native-purchases`/`react-native-purchases-ui` are native modules, changes here require a dev-client rebuild (`npx expo run:ios`/`run:android`), not just a JS reload — and won't do anything in Expo Go (which this app doesn't support anyway, see below) beyond the SDKs' own no-op "Preview API Mode".

## Translations (EN/ES)

All UI copy goes through a single i18n module, not per-screen strings:
- `src/constants/translations.js` — flat `{ en: {...}, es: {...} }` dictionary, **974 keys per locale**, verified key-for-key parity. A missing key on one side falls back silently to English via `useLanguage`'s `t()`, so a typo'd key won't crash, it'll just render the wrong language.
- `src/services/LanguageContext.js` — `LanguageProvider` (wraps the app in `App.js`) holds `locale` state, persists the choice to `AsyncStorage` under `fern_user_locale`, and exposes `t(key, params)` which does literal `{paramName}` substitution (e.g. `t('item_added_success', { item: itemName })` for a string like `"{item} was added..."`).
- `src/hooks/useLanguage.js` — thin `useContext` wrapper; every screen/component that renders user-facing text calls `const { t } = useLanguage();` directly (each component gets its own hook call — `t` is not threaded down as a prop, except `LanguageModal` which HomeScreen passes `t` into explicitly).
- `src/components/modals/LanguageModal.js` — the EN/ES picker sheet, opened from a button on `HomeScreen`.
- When adding new UI text: add the key to **both** `en` and `es` blocks in `translations.js` in the same edit (don't add English-only and leave Spanish to "later" — that's how the dictionary drifts out of sync), then call `t('your_key')` at the call site.
