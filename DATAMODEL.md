# DATAMODEL.md

Exhaustive reference for Fern Native's local persisted state and remote API surface. This is the companion doc to [CLAUDE.md](CLAUDE.md), which stays conceptual — this file has the exact field-by-field shapes. If you change a payload shape, an `AsyncStorage` key, or add a new Netlify function call, update this file in the same change.

There is no backend in this repo. Everything under "API reference" below is a remote Netlify function at `https://app.clickpickandcook.com/.netlify/functions/<name>`, except the one explicitly-flagged Groq call. The client is otherwise a thin, local-first cache over that remote API.

## Local-first sync architecture

`src/hooks/useSync.js` is the source of truth for app data at runtime. On mount it:
1. **Hydrates instantly** from the `fern_sync_cache` AsyncStorage key (`loadCache()`), so the UI has data before any network round-trip.
2. **Refreshes in the background** by POSTing `{ action: 'pull', userId, token }` to the `sync` function and re-persisting everything.

### `useSync.js` return shape

```js
data: {
  recipes: [],      // ← rv4_saved
  mealPlan: {},      // ← rv4_meal_plan
  shopping: [],       // ← rv4_master_shop
  books: [],            // ← rv4_books
  activities: [],        // ← rv4_activities
  followers: [],          // ← cpc_followed_bloggers
  userProfile: {},         // ← remi_explicit
  userStores: [],           // ← cpc_user_stores
  walletCoupons: [],          // ← coupons (confirmed from a live pull sample — NOT wallet_coupons, despite the push field/AsyncStorage key both being named wallet_coupons; see below)
  cbCovers: {},                // ← cb_covers (cookbook cover-photo URLs keyed by book id, e.g. { "cb_1786384300067": "https://...jpg" })
  tier: 'free',                 // ← tier ('free' | 'pro' | 'pro_max' — see below)
}
```

- **`pull()`** — POSTs `{ action: 'pull', userId, token }` to `sync`. Takes `result.data` (`saved`, `meal_plan`, `shopping`, `books`, `activities`, `followed_bloggers`, `remi_explicit`, `user_stores`, `coupons` — the wallet, see the `rv4_wallet_coupons` naming-trap note below — `cb_covers`, and `tier`), runs an emoji-corruption repair pass over `saved` (fixes `�`-corrupted `recipe.emoji` fields), maps it into the `data` shape above, calls `setData(next)`, then writes **both** the combined object to `fern_sync_cache` **and** each field out to its own individual key (`rv4_saved`, `rv4_books`, `rv4_meal_plan`, `rv4_master_shop`, `remi_explicit`, `cpc_followed_bloggers`, `cpc_user_stores`, `rv4_wallet_coupons`, `rv4_activities`, `rv4_cb_covers`, `fern_user_tier`). If the emoji repair changed anything, it immediately pushes the fix back to the server (including `wallet_coupons`/`coupons`, `activities`, `cb_covers`, and `tier`, so that push doesn't clobber any of them). **`available_coupons`, if present in the response, is intentionally ignored** — the client no longer reads or stores it (no `rv4_available_coupons` key exists anymore); the full coupon catalog is instead fetched live from the separate `fetch-coupons` function (see API reference) every time the Coupon Wallet's Browse tab opens.
- **`push(payload)`** — thin wrapper: POSTs `{ action: 'push', userId, token, ...payload }` verbatim; caller supplies the full payload, no AsyncStorage read.
- **`pushChangedFromStorage(changedData = {})`** — reads the 11 canonical keys fresh off disk (the original 7 plus `rv4_wallet_coupons`, `rv4_activities`, `rv4_cb_covers`, and `fern_user_tier`), builds `data: { saved, books, meal_plan, shopping, remi_explicit, followed_bloggers, user_stores, wallet_coupons, coupons, activities, cb_covers, tier, ...changedData }` — `wallet_coupons` and `coupons` are both set to the same array (see the `rv4_wallet_coupons` naming-trap note below) — (so in-memory `changedData` fields override what's on disk), POSTs `{ action: 'push', userId, token, data }`. This is what screens call after any local mutation.
- **`pushAllFromStorage()`** — `pushChangedFromStorage()` with no overrides, i.e. "push whatever's currently on disk."
- **Gap:** there is no push path for partial `userProfile` fields beyond the whole `remi_explicit` blob. Only the wallet coupons (pushed under both `wallet_coupons` and `coupons`), `activities` (the user's Family Hub activities), `cb_covers` (cookbook cover photos), and `tier` (the user's subscription plan) are round-tripped — the coupon catalog itself (`fetch-coupons`) is a read-only, unsynced live fetch, not part of push at all.

### Subscription tier sync (`tier`)

`tier` is `'free' | 'pro' | 'pro_max'` (matches `src/constants/tiers.js`'s `TIERS`), synced through the same `rv4_*`-style pattern as everything else, under the AsyncStorage key `fern_user_tier` and the pull/push field `tier`. RevenueCat (`src/services/RevenueCatContext.js`) is the on-device source of truth for the tier — the sync `tier` field exists so the **web app** (which has no RevenueCat SDK on its own) can read the same subscription status server-side, not so the native app can read it back (the app should always ask `useEntitlement()`/`useRevenueCat()` for gating decisions, never `data.tier` from `useSync`). `App.js`'s `MainAppContent` pushes the current RevenueCat tier via `pushChangedFromStorage({ tier })` on every app launch, once `user` is authenticated and RevenueCat's own `loading` flag has resolved (pushing while RevenueCat is still loading would push its temporary `FREE` fallback and clobber a real Pro/Pro Max tier server-side) — and again whenever `tier` changes mid-session (e.g. right after a purchase). This is a client-push design: the source of truth is Apple/Google's receipt validated by RevenueCat, mirrored into the backend on a best-effort basis: there's no webhook from RevenueCat into `clickpickandcook.com` in this repo, so the backend's copy of `tier` is only as fresh as the last time this app was opened by that user.

### `useSync.js` vs `useAuth.js` (known divergence)

`src/hooks/useAuth.js` has its own `syncPull(userId, token)`, called right after both login and signup, which independently POSTs `{ action: 'pull', userId, token }` to the same `sync` endpoint and writes the 7 individual keys (`rv4_saved`, `rv4_books`, `rv4_meal_plan`, `rv4_master_shop`, `remi_explicit`, `cpc_followed_bloggers`, `cpc_user_stores`). It has drifted from `useSync.pull()` in three ways worth knowing before touching either:

1. **It never writes `fern_sync_cache`.** Only the individual keys get written, so immediately post-login/signup the combined cache is stale until `useSync`'s own `pull()` fires on the next render.
2. **It skips the emoji-corruption repair pass** that `useSync.pull()` runs on `saved` — recipes with corrupted emoji are written verbatim at login time.
3. **Signup can clobber its own write:** `signUpWithSupabase` writes `remi_explicit = { userName: name }` first, then calls `syncPull`, which overwrites `remi_explicit` with `d.remi_explicit || {}` from the server response — if the new user has no server-side profile yet, the just-set `userName` gets wiped back to `{}`.
4. `syncPull` does write `fern_user_tier` (kept in sync with `useSync.pull()` when `tier` was added) but, like `cb_covers`, does **not** write `rv4_cb_covers` — see that key's row in the table below.

If you change the sync payload shape or add a new synced field, update both `useSync.pull()`/`pushChangedFromStorage()` **and** `useAuth.syncPull()`, or these will silently drift further.

### Auth session storage (separate from the sync cache)

Two stores, not one:
- **SecureStore key `fern_user`** — the primary, encrypted session: `{ id, email, token, refreshToken, ...user fields }`. Written on silent refresh, on the refresh-token fallback during a failed login, on successful login, and on signup. Deleted on `signOut()`.
- **AsyncStorage key `rv4_auth`** — a secondary, non-secure duplicate of just `{ id, email, token, refreshToken }`, written alongside every `fern_user` write. Read back only as a fallback source of `refreshToken` when the REST login call fails. **`signOut()` does not clear it** — a stale `rv4_auth` entry can survive logout.

Neither of these two keys is touched by `useSync.js` — `useSync` only ever consumes the `user` object it's given as a prop/param.

## "Move to Cookbook" save flow

Mirrors the web app's save dialog (cookbook picker + Cuisine + Meal Type dropdowns, confirmed against a live web session) — before this, the native app had no cookbook-selection step at all and every "Save to Recipes" action wrote straight to `rv4_saved` with no cookbook, defaulting cuisine/mealType to whatever the AI/source already supplied.

- **`src/constants/recipeOptions.js`** — `CUISINE_OPTIONS` (21 entries incl. an intentional duplicate `'Italian'`, matching the web dropdown exactly) and `MEAL_TYPE_OPTIONS` (`Breakfast`/`Lunch`/`Dinner`/`Dessert`/`Snack`/`Appetizer`, same enum the `recipe_search` AI prompt already used). `CUISINE_OTHER_VALUE` is a sentinel selected by the web-equivalent "Other / Type my own..." option, which reveals a free-text input for a custom cuisine.
- **`src/components/modals/SaveToCookbookModal.js`** — the shared picker UI (bottom-sheet card + tap-to-open checkmarked option lists, since RN has no native `<select>`). Takes `books` (raw `data.books`), `initialBookId`/`initialCuisine`/`initialMealType` (prefilled from the recipe being saved/moved), and calls `onSave({ bookId, cuisine, mealType })` — `bookId: null` means "My Recipes" (no specific cookbook).
- **`src/components/RecipeDetailModal.js`** — the shared recipe viewer wires this in centrally. The bottom Save button: for a recipe that is **not saved yet** (`isAlreadySaved === false`, button reads "Save to Recipes") a normal tap opens `SaveToCookbookModal` first, like the web app (changed 2026-10-11 — before, it silently saved with no cookbook, which users reported as "sometimes just adds it"); for an **already-saved** recipe a tap still calls `onSaveNote` directly (updates the note). `SaveToCookbookModal` can also always be opened via the small `▾` chevron (its own nested `TouchableOpacity`, inside — but hit-tested independently of — the main button) or by long-pressing the button; all routes go through `handleOpenSaveToCookbook`. Both are no-ops if `onSaveToCookbook` isn't supplied. The button renders as a two-part "SAVE │▾" split style whenever `onSaveToCookbook` is supplied, signaling the dropdown affordance exists; when confirmed, `SaveToCookbookModal` calls `onSaveToCookbook({ bookId, cuisine, mealType })`. New props: `books`, `onSaveToCookbook`. The picker works **regardless of `isAlreadySaved`** — for a new recipe it assigns a cookbook at save time, for an already-saved one (reopened prefilled via `initialBookId={recipe?.bookIds?.[0]}`) it re-tags/moves it in place. The separate "SAVE NOTE" button/`onSaveNote` prop is untouched either way — note-editing never goes through this modal.
- **Why `onSaveToCookbook` never closes the recipe detail view on success** (each implementation below patches `selectedRecipe` in place instead of nulling it out): `SaveToCookbookModal` is a second RN `<Modal>` nested inside `RecipeDetailModal`'s own `<Modal>`. Closing the *outer* one (e.g. via `setSelectedRecipe(null)`) while the *inner* one is still open/tearing down left the native modal stack broken and unresponsive on iOS — the whole screen appeared to "get stuck" (no touches registered) after a cookbook save. The fix: `RecipeDetailModal.handleConfirmSaveToCookbook` only ever closes the inner `SaveToCookbookModal` (`setIsSaveToCookbookVisible(false)`) after `onSaveToCookbook` resolves; none of the four handlers below close the outer detail view anymore.
- **Per-caller wiring** — every screen that renders `RecipeDetailModal` passes `books={data.books}` and an `onSaveToCookbook` handler; each handler branches on whether a matching recipe already exists in `rv4_saved` (by id or title): if so it updates that entry's `cuisine`/`mealType`/`_bookIds` in place, otherwise it appends a new entry with them — then pushes+pulls, then patches local `selectedRecipe` state (`category`/`meal`) so the detail view reflects the change without closing:
  - `useAiRecipeCollection.js`'s `saveToLibrary(detailRecipe, note, overrides)` takes an optional third `{ bookId, cuisine, mealType }` argument for the append case; `saveSelectedToCookbook({ bookId, cuisine, mealType })` (no `onDone` callback — see above) wraps both branches for the currently-`selectedRecipe`. `HomeScreen.js` (via `activeAiRecipeCollection`) and `FamilyScreen.js` (via `mealPlanRecipes`) both get this for free through the one shared hook.
  - `SearchScreen.js` has its own independent save implementation (see CLAUDE.md) — `persistSelectedRecipeNote` (`onSaveNote`) is back to its original shape (update-in-place note edit, or append a plain new entry with no cookbook — exactly the pre-this-feature behavior), and a separate `persistSelectedRecipeToCookbook({ bookId, cuisine, mealType })` (`onSaveToCookbook`) handles both the update-in-place and append-with-cookbook cases.
  - `EventPlannerIntakeModal.js` — `handleSaveRecipe` (`onSaveNote`) is back to its original plain-save behavior (alerts and blocks if already saved, no cookbook prompt); `handleSaveRecipeToCookbook({ bookId, cuisine, mealType })` (`onSaveToCookbook`) is the new one — unlike the plain version, it updates the existing entry's `_bookIds`/`cuisine`/`mealType`/`category`/`meal` in place instead of blocking.
  - `RecipesScreen.js`'s `persistSelectedRecipeToCookbook` — added alongside its existing `persistRecipeNote` (`onSaveNote`, unchanged); always an update-in-place here, since this screen only ever shows recipes already in `rv4_saved`. Distinct from `AddRecipesToCookbookModal` (that screen's bulk multi-recipe cookbook picker), which is unaffected by this per-recipe flow.

## API reference

All endpoints are `POST https://app.clickpickandcook.com/.netlify/functions/<name>` with `Content-Type: application/json` unless noted otherwise. Most calls also send a `User-Agent: FernApp/1.0 (myaifern.com)` header (a few inline call sites omit it — not meaningful, just inconsistent).

### `ai` — general-purpose AI proxy (heaviest-used endpoint, 10 call sites)

Two distinct payload shapes are in use:
- **Structured** (most callers): `{ system, messages: [{ role: 'user'|'assistant', content }], feature?, locale, token, userId? }`. Response: `json.content[].find(p => p.type === 'text').text` (fallback `json.message`/`json.reply`), then the caller loose-JSON-parses that text (regex-extracts the first `{...}`/`[...]` if `JSON.parse` fails outright).
- **Legacy/simple** (`HomeScreen.js`'s Family Hub voice flow only): `{ message, context: 'family_hub', userId, token, locale }` → response `{ reply }`. This is the one caller that doesn't use the `messages` array shape — don't copy it for new features.

### `fern-speak` — text-to-speech

Payload: `{ text, locale, token }`. Response is **not JSON** — raw mp3 bytes read via `response.arrayBuffer()`, manually base64-encoded, written to `FileSystem.cacheDirectory + 'fern-*.mp3'`, played with `expo-audio`. Called from `useContinuousMic.js`, `useFernVoice.js`, and `FindScreen.js` (dead screen).

### `auth` — login

- `{ action: 'refresh', refreshToken }` → `{ success, token, refreshToken }` (or a falsy/failed response, treated as `null`).
- `{ action: 'login', email, password }` → `{ user, access_token|token, refresh_token|refreshToken, error?, message? }`. On failure, `useAuth.js` falls back to the refresh-token flow using the `rv4_auth` AsyncStorage key. Signup does **not** go through this endpoint — `signUpWithSupabase` uses the Supabase JS SDK directly.
- Caller: `src/hooks/useAuth.js` only.

### `sync` — pull/push of all user data

See "Local-first sync architecture" above for the full pull/push shape. Payload is always `{ action: 'pull'|'push', userId, token, [data] }`. Called from `useSync.js` and independently from `useAuth.js`'s `syncPull`.

### `get-recipe-image`

Payload: `{ query, token }`. Response: `{ url }` (returns `null` silently on any error — callers treat a missing image as normal, not exceptional). Called from `src/utils/recipeImage.js`'s `fetchRecipeImage`, used by `eventPlannerService.js`, `useAiRecipeCollection.js`, `SearchScreen.js`, `HomeScreen.js`, `RecipesScreen.js`, `EventPlanResultModal.js` (dead), `TwentyMinDinnerModal.js`, `EventPlannerIntakeModal.js`, `MealPlannerImage.js` (the AI Meal Planner's per-meal photos on the day cards and detail view — looked up by meal title, remembered for the session, emoji fallback; mirrors the web planner).

### `upload-photo`

Response: `{ success, url }`, where `url` points at Supabase storage (`https://axqkdhzcfcroxlkducea.supabase.co/storage/v1/object/public/recipe-photos/<fileName>`). Caller: `src/services/uploadPhotoService.js`'s `uploadPhoto`, used by `RecipesScreen.js`'s `NewCookbookModal` to upload a cookbook cover photo — the returned `url` is stored in `rv4_cb_covers` (see local storage key table), not on the book object itself.

### `meal-planner`

Payload varies by `action` — `load_plan`, `generate`, `regenerate_meal`, `save_plan`, and `shopping_list` are all implemented client-side:
- `{ action: 'load_plan', userId, token }` → `{ plan: { days: [{ dayLabel, meals: [{ slot, title, emoji, time, difficulty, cuisine, ingredients: [""], instructions: [""] }] }] } }`. Normalized (adds local `id`s per day/meal) in `src/services/mealPlannerService.js`'s `fetchMealPlan`. Caller: `MealPlannerModal` via `HomeScreen.js` (`openMealPlannerModal`/`loadMealPlan`), which loads once per modal open. Tapping a meal feeds its already-embedded `ingredients`/`instructions` straight into the same `useAiRecipeCollection`/`RecipeDetailModal` flow used everywhere else (source `meal_planner`, folded into `HomeScreen.js`'s shared `selectedAiRecipe` chain) — no second AI call needed, it only auto-fetches an image via `get-recipe-image` the way that flow always does.
- `{ action: 'generate', userId, locale, savedRecipes: [""], plan: { days: [...] } }` → same `{ plan: { days: [...] } }` response shape as `load_plan`. Notably **no `token`** in this payload — confirmed from a captured request, unlike every other call in this app. `savedRecipes` is the user's saved-recipe titles (`data.recipes.map(r => r.title)`, duplicates included, not deduped); `plan` is the *currently displayed* plan round-tripped back (stripped of the client's local `id` fields via `denormalizeDaysForApi`) so the backend knows what's already been suggested and can avoid repeating it. Caller: `mealPlannerService.generateMealPlan`, triggered from `MealPlannerModal`'s "↺ Regenerate" button or the Preferences screen's "✨ Generate My Week" button, both gated behind a native confirm (`Alert.alert`) since it replaces the currently-loaded plan.
- `{ action: 'regenerate_meal', userId, locale, plan: { days: [...] }, dayIndex, slot }` ("Swap this meal") → `{ meal: { title, emoji, description, time, difficulty, cuisine, slot, ingredients: [""], instructions: [""], notes } }` — a single replacement meal, plus `description` and `notes` (a make-ahead/serving tip, rendered as the 💡 callout in `MealPlannerRecipeDetailView`) that `load_plan`/`generate` never include. No `token`, matching `generate`. **`dayIndex` + `slot` are the only identifiers for which meal to replace** — not title, since titles can repeat — so the caller (`HomeScreen.js`'s `handleSwapMealPlannerMeal`) splices the response into `mealPlannerDays[dayIndex].meals` by matching `slot`, keeping the existing local `id`, rather than searching by name.
- `{ action: 'shopping_list', userId, plan: { days: [...] }, locale }` → expected `{ shoppingList: [{ category, items: [""] }] }` (no confirmed sample response yet, so `mealPlannerService.fetchMealPlannerShoppingList` also checks `shopping_list`/`list` keys and a bare top-level array as fallbacks, degrading to an empty list rather than crashing if the real key differs). No `token`, matching `generate`/`regenerate_meal`. Caller: `MealPlannerShoppingListView` via `HomeScreen.js`'s `loadMealPlannerShoppingList`, triggered when the "🛒 Shopping List" button is tapped. "🛍️ Shop with Fern — section by section" flattens every group's items into one synthetic recipe and runs it through the same `addRecipeIngredientsToShoppingList` (`src/utils/shoppingListSync.js`) + `pushAllFromStorage`/`pull` flow every other "add to shopping list" action in the app uses, writing into `rv4_master_shop` — then closes the meal planner modal and navigates to the `Shopping` tab.
- `{ action: 'save_plan', userId, token, plan: { days: [...] }, preferences: { mealsPerDay, whichMeals: [""], cookTimeMax, servings, dietary: [""], disliked: [""] } }` → `{ success: true }`. Unlike `generate`/`regenerate_meal`, this one **does** carry `token`. Fired (fire-and-forget, not awaited by the UI) right after a successful `generate` *or* `regenerate_meal` in `HomeScreen.js`, passing the resulting plan plus whatever preferences produced it — collected from `MealPlannerPreferencesScreen.js`'s meals-per-day/which-meals/cook-time/servings/dietary/avoid-ingredients controls (lowercased for `whichMeals`/`dietary`), or the last-used preferences (`HomeScreen`'s `mealPlannerPreferences` state, defaulted to `{ mealsPerDay: 1, whichMeals: ['dinner'], cookTimeMax: 45, servings: 4, dietary: [], disliked: [] }`) when triggered from the quick "↺ Regenerate" button instead of the Preferences screen.

### `loyalty`

Payload: `{ action: 'match', phone_hash }`, where `phone_hash` is a client-side SHA-256 hex digest (`src/utils/sha256.js`) of the digits-only phone number — the raw number never leaves the device. Response: `{ success, points, tier, linkedCards[], message }`. Caller: `src/services/loyaltyService.js`'s `matchLoyaltyCard`, used by `LoyaltyCardModal` via `HomeScreen.js`; the result is cached locally under `rv4_loyalty_card` (see local storage key table above) to drive the Home loyalty tile's linked state.

Three more `action`s manage a **separate** list of manually-entered per-store loyalty card numbers (store name + card number, not phone-hash-based) — no local caching, the `list` response is the sole source of truth, refetched every time `LoyaltyCardModal` opens:
- `{ action: 'list', token }` → `{ success, linkedCards: [{ storeName, cardNumber, linkedAt }] }`. Caller: `loyaltyService.fetchLinkedStoreCards`, called from `HomeScreen.js`'s `openLoyaltyModal`.
- `{ action: 'link', token, storeName, cardNumber }` → `{ success, linkedCards[], message }`. Caller: `loyaltyService.linkStoreCard`, from the modal's "Store Loyalty Cards" add form.
- `{ action: 'unlink', token, storeName }` → `{ success, linkedCards[] }`. Caller: `loyaltyService.unlinkStoreCard`, from each card row's "Remove" link.

All three take **`token` only** — no `userId`, no `phone_hash` — and all return the full updated `linkedCards[]`, which the caller just uses to replace local state directly rather than re-fetching.

### `instacart-list`, `kroger-list`, `albertsons-list` — send the shopping list to a store

Three separate functions, one per retailer, all called from `src/services/storeShoppingListService.js` via `ShoppingScreen.js`'s "SEND LIST TO" row (Instacart/Kroger/Safeway buttons). None take a `token`.

- `instacart-list` — payload `{ items: [""], title, linkbackUrl: 'https://app.clickpickandcook.com' }`. Response: `{ url }` — Instacart accepts the whole list in one shot, so `url` is a ready-to-open shopping list link. Opened via `Linking.openURL` (no in-app webview — none is installed in this project; see below).
- `kroger-list` — payload `{ items: [""], title, banner: 'Kroger', bannerUrl: 'https://www.kroger.com' }`. Response: `{ url, matched, total, provider, remainingItems: [""] }`. Kroger only supports a single-item search deep link, so `url` is a search-results page for just the *first* item — everything else comes back in `remainingItems`. The app opens `url` via `Linking.openURL` and shows `StoreRemainingItemsModal` with the rest, so the user can copy/paste them into the store's own search box.
- `albertsons-list` — same request/response shape as `kroger-list`, but payload uses `banner: 'Albertsons'`, `bannerUrl: 'https://www.albertsons.com'` (this is what the Shopping screen's "Safeway" button actually calls — Albertsons owns Safeway and this is the shared backend for both banners).

**No in-app browser yet**: this project has no webview library installed (`react-native-webview`, `expo-web-browser`, etc. are all absent from `package.json`). Adding one is a native-module change requiring `npx expo install` + a dev-client rebuild, so for now these links open via `Linking.openURL`, which hands off to the system browser rather than staying in-app. Revisit if/when an in-app browser is added.

### `geocode` — `GET /.netlify/functions/geocode?q=<storeName>&zip=<zip>[&token=<token>]`

One of two **GET** endpoints (the other is `fetch-coupons`, below), no body. Response: `{ lat, lon, address, source }`, validated and returned as `{ lat, lon, lng: lon, address, source }` (or `null` on failure). Caller: `src/services/storeLookupService.js`'s `findStoreLocationByZip`, used by `HomeScreen.js`'s store-management UI. **The function only searches `q` (it ignores `zip` when a Google key is set), so the client puts the ZIP inside `q`**: `"<name> grocery store near <zip>"` (same as the web app), retrying `"<name> <zip>"` if that finds nothing.

### `fetch-coupons` — `GET /.netlify/functions/fetch-coupons`

The other **GET** endpoint — no query params, no body, no `token`/`userId`. Response: `{ coupons: [{ id, code, image, store, title, expiry, source, category, discount, redemption, description }] }` — confirmed live (102 items at time of writing): `redemption` is `'digital'`/`'link'`/`'code'`, `store` can be `''`, `image` can be `null`, `expiry` is an ISO datetime string. This is the full coupon catalog — same shape the sync payload's now-unused `available_coupons` field used to carry (see the removed-key note above). Caller: `src/services/couponsService.js`'s `fetchAllCoupons`, called by `HomeScreen.js`'s `openCouponWallet` every time the Coupon Wallet's Browse tab is opened — not cached or synced, always a live fetch. Normalized client-side via `src/utils/couponNormalize.js`'s `normalizeCoupon`/`normalizeCoupons`. Contrast with `rv4_wallet_coupons`/`data.walletCoupons` (the user's *saved* coupons, sourced from the `sync` function's `coupons` field, not this endpoint) — Browse shows the live catalog from here, My Wallet shows the synced wallet array.

### `insider-deals` — Pro brand-partnership offers

Payload: `{ token }` (no `userId` — the backend resolves the user from the verified token). Response: `{ deals: [{ brand, title, description, image_url, deal_code, valid_until, featured }], updatedAt }` for a Pro/Pro Max user, or `{ proOnly: true }` when the backend's own record (`user_data.tier`) says the user is free. `deals` is expected to be empty until real brand partnerships are added server-side (`brand_deals` table) — the modal's "Deals coming soon" state is the normal case today. The backend swallows its own errors and returns `{ deals: [] }`, so an empty list can also mean a server-side failure. Because `user_data.tier` is filled by the client-push described under "Subscription tier sync", a user who just subscribed can see `proOnly` until the next app launch pushes the new tier. Caller: `src/services/insiderDealsService.js`'s `fetchInsiderDeals`, used by `InsiderDealsModal` (Home "Insider Deals" tile, gated by `FEATURE_TIERS.insider_deals` = Pro). Mirrors the web app's `openInsiderDeals()`.

### `share` and `share-cookbook` — hosted share links

Both called from `src/services/shareService.js`. Neither takes a `token`; both return `{ success, url }` (or `{ error }`). The recipe/cookbook objects are mapped from native's normalized shape by `toSharedRecipe` to the field names the backend reads (`title, emoji, cuisine, mealType, time, difficulty, description, servings, ingredients[], instructions[], notes, photo`); placeholder strings like "No ingredients listed yet" are dropped, and `photo` is sent only when it is an `http(s)` URL.

- `share` — payload `{ recipe, message, senderName, siteUrl }`. The backend inserts a row into Supabase `shared_recipes` and returns `https://app.clickpickandcook.com/share.html?id=<id>` (it checks the insert result and returns a 500 `{ error }` if it fails). Caller: `RecipeDetailModal`'s "✨ Share" button → `createRecipeShareLink` → the OS share sheet (`Share.share`). No second `<Modal>` is opened from inside `RecipeDetailModal` on purpose (see the nested-modal note under "Move to Cookbook").
- `share-cookbook` — payload `{ cookbook: { name, colorId, coverUrl, recipes }, message, senderName, siteUrl }`. `coverUrl` is the hosted cover URL (the web app sends a resized base64 image instead). Returns `<siteUrl>/cookbook-share.html?id=<id>`. **Known backend limitation:** `share-cookbook.js` keeps shared cookbooks in an in-memory object (`cookbookShareData`, with a comment "replace with database in production"), not in Supabase — so a link can 404 once the serverless instance that created it is recycled. This affects the web app's cookbook sharing identically; native inherits it. Caller: `RecipesScreen.js`'s cookbook-detail "Share" button → `ShareLinkModal` (note + name fields) → `createCookbookShareLink` → the OS share sheet. The web app's "background" picker is not ported (the backend does not store it for cookbooks anyway).

### `personal-shopper-plan` — Personal Shopper (Pro Max)

`POST`, no `token`/`userId` in any action. Caller: `src/services/personalShopperService.js`, used only by `PersonalShopperModal` (opened from `HomeScreen.js`'s Personal Shopper tile — previously that tile just navigated to the Shopping tab). Gated by `FEATURE_TIERS.personal_shopper` (Pro Max).
- `{ action: 'start', locale, userProfile, lat, lon, mealPlan, savedRecipes: [{title}], activities, activityHistory }` → `{ reply, systemPrompt, forecast[], recurringActs[] }`. `savedRecipes` is titles only (max 25).
- `{ action: 'suggest_dinners', locale, savedRecipes, forecast, activities, mealPlan, userProfile, deals?, dealsStore? }` (`userProfile` may also carry `householdSize`, `dietary`, `vibe` from the "About you" questions — the backend adds them to the prompt as plain data) → `{ pitch, suggestions: [{ dayName, date, title, reason, quick }] }`. `deals` (`[{ name, salePrice, isBogo }]`, max 30) and `dealsStore` are optional and only sent by the store-arrival flow after a flyer scan; the backend adds them to the prompt as data so dinners are built around the sale items (omitted = unchanged behaviour). The backend computes dates in **UTC**, so for evening users west of UTC "today" is never suggested; the client keeps a suggestion's date only if it falls inside the local rolling week (`buildRollingWeekDateKeys`) and drops days that already have a Dinner.
- `suggest_dinners` also takes `savedRecipes` as `[{title, ingredients[]}]` (first 10 ingredient names each) and returns, per suggestion, `source` (`'cookbook'` only if the title exactly matches a saved recipe, else `'ai'`) and `saleItems: [{name, price, isBogo, store}]` — validated server-side against the sent `deals` (and, for cookbook recipes, against the recipe's ingredients), so the UI never shows a sale item the dish doesn't use. `PersonalShopperModal`'s dinners panel shows an "On sale" list (each item → `fetchDealRecipeIdeas`, tap an idea to swap it into the week), then the dinners grouped "From your cookbook" / "Fern found" with sale-item chips.
- `suggest_dinners` (flow update): `userProfile` may also carry `craving` (what they're in the mood for this week, asked every run, never remembered) and `dinnersWanted` (the server plans only that many of the empty days). Each suggestion also returns `sides: string[]` (1-2 sides so every dinner is a complete meal); the client saves them on the `rv4_meal_plan` entry as `sides`, adds them to the shopping list, and shows them on the week view. After the list is built, "Walk me through it" steps through the store sections one at a time.
- `{ action: 'get_recipe_ingredients', recipe: { title, ingredients }, alreadyHave[], onList[] }` → `{ needed[], alreadyHave[] }` (string matching, no AI).
- `{ action: 'build_list', items[], locale }` → `{ sections: [{ id, name, emoji, items[] }] }`.
- `{ action: 'chat', conversationHistory, userMessage, locale }` → `{ reply }`; history includes the `start` system prompt as role `system`.

**Trip flow (current):** `PersonalShopperModal` now runs one flow for every entry point: (1) `mylist` — shows the unchecked items already in `rv4_master_shop` (add more, then continue; skipped if empty); (2) flyer — scan, or use shared `store-deals`; (3) one "this week" confirm panel (`fern_shopper_prefs` defaults prefilled: 4 people / no restrictions / 5 dinners, plus an optional "in the mood for" chip — no pantry or question chain); (4) `meals` — the app ranks deals client-side (`pickStarDeals`: saving, BOGO, food-ness; one per product family), asks `ai` (`fern_chat`, `fetchDealRecipeIdeas`) for 3 complete dinners (main + 1-2 `sides`) per star item with household/diet/week as a note, pre-picks N round-robin, and lets the user tick/preview/swap; confirming writes dinners (with `sides`) into the open days of `rv4_meal_plan`, fetches each dinner's ingredients (`fetchMealPlanRecipeDetail`), and (5) builds ONE sorted list = existing list + dinner ingredients + sides (`build_list`), written to `rv4_master_shop`. The old week-review/activities/per-recipe-ingredient/pantry steps are no longer reached. Deals now also carry `originalPrice`, `savings`, `category`, `cookable`, `dealScore` for savings math and star ranking.

Writes made by the flow: confirmed dinners → `rv4_meal_plan` (`{ slot: 'Dinner', title, emoji, recipeId? }`, pushed as `meal_plan`); recurring activities → `rv4_activities` (pushed as `activities`); final list → `rv4_master_shop` via `addRecipeIngredientsToShoppingList` (grouped by recipe; manual adds use `recipe: 'Manual Add'`), pushed as `shopping`. Grocery names stay English in synced data. Not ported from web: voice mode and the in-store guide.

### `store-deals` — current weekly-ad data already on file for the user's saved stores

`POST { token, stores: [""] }` (saved store names from `cpc_user_stores`, e.g. `"Publix - Blowing Rock"`, `"Harris Teeter #123"`). Response `{ stores: [{ requested, store, scannedAt, validDates, itemCount, items: [{ name, brand, category, price, unit, originalPrice, savings, isBogo }] }] }` — only stores that have a *current* flyer. This is the read side of the shared per-store scan data `scan-circular` saves to Supabase `circular_scans`/`circular_prices`: scans are **shared across all users** (prices only; user ids are never returned). "Current" = the flyer's own printed `valid_dates` haven't ended (parsed server-side; ended > 1 day ago = excluded), else scanned within 7 days. A saved store name matches a scan's store by chain (text before ` - ` / `#`), so every Publix shares Publix scans. Items are food-first, then ones with a stated saving/BOGO; max 150 per store. Caller: `src/services/storeDealsService.js` (`fetchStoreDeals`, best-effort, `[]` on any failure), used by `PersonalShopperModal`'s flyer step: if deals are on file Fern offers "Use these deals" / "Scan a newer flyer" instead of asking for a photo (top 15 per store go to `suggest_dinners` as `deals`, each tagged with its `store`; with more than one store the planner says which store to buy each sale item at). A fresh scan keeps other stores' stored deals alongside it. **Regions:** native scans now send `zipCode` (first saved store's ZIP, parsed from its address by `src/utils/storeZip.js`), and `store-deals` accepts `zips: { [storeName]: zip }` so a store with a known ZIP only gets scans from the same area (same first 3 digits) or older scans saved with no ZIP; no ZIP known = no filtering. **Wrong-photo undo:** `POST { token, discardLatest: true }` → `{ discarded: bool }` deletes the caller's own most recent scan (made in the last 30 min) from `circular_scans`/`circular_prices`. `PersonalShopperModal` shows a "scancheck" panel after every scan (store, dates, item count, sample items, warnings when the store isn't a saved one or <5 items); "Wrong photo, retake" restores the previous deals and calls `discardLatestScan`. Dinner sale tags are matched client-side from each recipe's real ingredients (`ingredientHasSaleItem`: main-noun match, rejects a different qualifier like black vs bell pepper), not from the AI's `saleItems`.

### Groq Whisper (not a Netlify function — direct external call)

`https://api.groq.com/openai/v1/audio/transcriptions`, called from `useContinuousMic.js` via `FileSystem.uploadAsync` (multipart, `{ model: 'whisper-large-v3', language: locale }`), authenticated with `EXPO_PUBLIC_GROQ_KEY` as a bearer token embedded in the client. This is the one place the app talks to a third party directly instead of proxying through `clickpickandcook.com` — worth knowing before assuming "all network calls go through the Netlify functions."

## Coupon matching & savings (ShoppingScreen)

`src/utils/savings.js` holds the savings math (`dealSaving`, `sumSavings`, `fmtMoney`, `priceNum`), the flyer sale-matching helpers (`ingredientHasSaleItem`, `matchSaleItems` — shared with `PersonalShopperModal`), coupon matching and the weekly ledger. `ShoppingScreen` builds its coupon pool from the wallet (`data.walletCoupons`) plus the live `fetch-coupons` catalog (non-expired, wallet first) and calls `matchListItems(items, weekDeals, coupons)` (coupons are filtered to non-food categories only — Household & Cleaning, Health & Beauty, Baby & Kids, Pet Care — via `isNonFoodCoupon`; food coupons are brand-specific and never fit a recipe ingredient): each list item gets at most one flyer deal (`ingredientHasSaleItem`) and up to 3 coupons, each `level: 'match'` (every key word of the item is in the coupon title, and a single-word item is the title's main noun) or `'possible'` (the item's main noun appears in the title/description). `parseCouponValue` reads `$`, `¢` and `%` from the discount label; percent coupons have no computable amount. `normalizeCoupon` now also carries `redemption` (`digital`/`link`/`code`), `url` and `realCode` (the catalog's own code, not the id fallback). A "Coupons for your list" card (shown whenever any non-food coupon matches a list item, bought or not) lists them with an "Add to wallet" button (writes `rv4_wallet_coupons` + `fern_sync_cache.walletCoupons`, pushes both `wallet_coupons` and `coupons`). The "Before you check out" card appears once the user taps "I'm done shopping" or ticks every item, and lists coupons that matched ticked items (code / open link / digital note + "give your phone number at the register"). Coupon savings only count when the user marks them used.

**Shopping list names:** ingredient lines are converted to buyable names (quantities, units, sizes and prep notes dropped — "1/4 cup soy sauce" → "Soy sauce") by `src/utils/shoppingName.js` `toShoppingName`, applied in `addRecipeIngredientsToShoppingList` and `PersonalShopperModal`'s `addListItem`. The Personal Shopper "Your list" panel's "Tidy up list" button applies it to items already on the list.

**Free/Pro scan upsell:** after a flyer scan, `ScanCircularModal` shows (only when `hasAccess(FEATURE_TIERS.personal_shopper)` is false) an "Fern found $X in savings on this flyer — unlock meals, coupons and your weekly savings" card, with `$X` from `sumSavings` over the scanned items; its button closes the modal and opens the plans screen after ~450 ms.

**"Too good to pass up"** (ShoppingScreen): `tooGoodCoupons` scores every catalog/wallet coupon (any category — it offers to add the item, so food is fine) not already matched to the list (`$ amount + percent/20 + 3 for BOGO/free`), keeps score ≥ 2, top 4. Relevance filters: retailer coupons must be for a saved store (no-store manufacturer coupons pass), non-grocery offers (devices, delivery, memberships) are dropped, and baby / pet / health & beauty coupons only show when a list item matches. Its button adds the item (`couponItemName` of the coupon title, `recipe: 'Coupon deal'`) to `rv4_master_shop` and the coupon to the wallet in one tap.

**Browsing sale items:** `src/components/SaleItemsList.js` (search + items grouped by flyer category, biggest savers first, one-tap "+ Add") is shared by the Personal Shopper scan check ("See all N sale items", adds through `addListItem` into the trip's list) and a "This week's sales" card on `ShoppingScreen` (reads `fern_week_deals`, adds straight to `rv4_master_shop`; **shown only once a flyer has been scanned** — the empty "Scan a flyer and every sale item will show up here" box was removed, so `sale_list_week_empty` is now unused).

**The shopping trip (one screen, Oct 2026):** `ShoppingScreen` is the whole store trip, open to every plan for now. A 4-step strip (List · Sales · Coupons · Meals) scrolls to: (1) the list + add row; (2) `components/trip/FlyerSection.js` — "Use this ad" from `store-deals` (flyers other shoppers scanned for the user's saved stores, when nothing is loaded yet) or scan a photo via `scanCircular`, with "Wrong photo, retake" (restores `fern_week_deals` via `replaceWeekDeals` + `discardLatestScan`) — then "This week's sales" (`SaleItemsList`, each item has Recipes / + Add); (3) coupons ("Too good to pass up", "Coupons for your list", and "Before you check out" after "I'm done shopping"); (4) `components/trip/WeekMealsSection.js` — `pickStarDeals` (now in `src/utils/starDeals.js`, shared with PersonalShopperModal) picks 2–4 star sale items, `fetchDealRecipeIdeas` gives complete dinners (main + sides) per item, tick/preview/"3 different dishes"/"Use a different sale item", then one tap writes the dinners to `rv4_meal_plan` (open days in the rolling week, pushed as `meal_plan`) and every ingredient + side to `rv4_master_shop` through `addRecipeIngredientsToShoppingList` (`persistShopping`). Entry points: Home "Scan a flyer", the Personal Shopper tile, and the store-arrival notification all `navigate('Shopping', { tripStart })`; the savings notification taps `navigate('Shopping', { tripDone })`. `PersonalShopperModal` is no longer reachable from the UI (kept as dead code for now).

**Leaving the store:** geofence regions now set `notifyOnExit: true` (needs the next native build to take effect for already-registered regions; JS re-registers them on launch). `notifyArrival` writes device-only `fern_trip_started` `{ store, at }`; on an Exit event `storeGeofencing.notifyDeparture` sums `fern_savings_ledger` entries with `at >= trip start` (`summarizeSince`, ticked-off sale items + coupons marked used) and, if > $0, posts "You saved $X on this trip — $A on sale items and $B in coupons" (`data.type = 'store_exit'`, 30-min cooldown key `exit:<storeKey>`). Both the arrival alert and this "you saved $X" alert are **Pro Max only** (bought or admin-granted; `hasProMax()` in `storeGeofencing.js` gates `notifyArrival`/`notifyDeparture`, so Free and Pro get no store notifications, from the background task or the foreground poll). The arrival notification text is the flyer/dinners one.
